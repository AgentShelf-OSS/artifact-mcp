# Artifact MCP v1.15.0

## Listen sounds like an audiobook

- **Pacing.** Pocket cannot synthesize pauses, so the player now schedules silence between
  spoken blocks: 600 ms between paragraphs, 1200 ms before and 900 ms after a heading, 1800 ms at
  a scene break, 1500 ms when continuing into the next ereader chapter, and 150 ms between voice
  segments of one paragraph. A visible `<hr>`, `data-artifact-reader-break` or an ereader break
  block marks a scene. `data-artifact-reader-pause="none|short|long|scene"` overrides the pause
  before a block. The expanded player offers Natural, Short and Off; speed scales the pauses.
- **Loudness matching.** The 21 Pocket presets differed by up to 15 dB. Each now has a measured
  gain toward about -19 LUFS (capped at +12 dB), and the Web Audio path ends in a limiter, so
  cast voices sit at the same level.
- **Lock-screen and headset controls.** Where the Media Session API exists, Listen publishes the
  chapter, voice or role, artifact title and app icon, and handles play, pause, stop, 15-second
  rewind and previous/next block. On WebKit it requests the `playback` audio session first.
  Background playback after the screen locks still depends on the browser.
- **More than one listener.** `TTS_WORKER_CONCURRENCY` (1-8, default 3) replaces the single
  in-flight request per speech worker in both runtimes, so a voice preview during playback, a
  second tab or a second listener no longer receive an immediate `429`. Requests beyond the limit
  still receive `429` with `Retry-After: 2`. Invalid values fail startup configuration.
- Chunk sizing follows each role's voice.

A new reader regression, `reader-pacing`, runs against both runtimes. `reader-prefetch` now turns
pauses off because it measures seamless prefetch.

## Schema and configuration

The schema remains 39. New optional variable: `TTS_WORKER_CONCURRENCY` (default 3). Production
Pocket workers queue up to two waiting requests; the default matches one active request plus
that queue.

## Deployment and rollback

Verify the release checksums, manifest, and attestations before installation. Keep the current
v1.14.0 binary and deployment record for rollback. A rollback to v1.14.0 uses the same schema
and restores the previous unpaced, single-request behaviour.
