# Artifact MCP v1.17.0

## Republish by artifact key

Agents can now republish the same artifact without remembering its id.

- `publish_artifact` and `publish_bundle` accept an optional `artifact_key`, a stable name the
  publisher chooses, for example `project/topic`. Grammar: `^[a-z0-9][a-z0-9._/-]{0,127}$`.
- If no artifact in the organization has the key, publication creates one as before and stores
  the key. If the key exists, the call updates that artifact in place with `update_artifact`
  semantics: same id and URL, revision increments on change, omitted metadata is kept.
- The result adds `revision`, `artifact_key`, and `created` (`true` for a create, `false` for an
  update). `list_artifacts` and `read_artifact` show `artifact_key` when it is set.
- A caller that may not update the keyed artifact gets the same refusal as `update_artifact`.
  Keys never match across organizations. Deleting an artifact frees its key; an administrator
  move to another organization clears it.

See `docs/adr/0015-publish-upsert-by-artifact-key.md` and "Republishing by artifact key" in
`docs/mcp-api.md`.

## Schema and configuration

The schema moves from 39 to 40. Migration 040 adds a nullable `artifacts.artifact_key` column and
a partial unique index on `(org, artifact_key)`. It changes no existing rows. There is no new
configuration.

## Deployment and rollback

Back up the database before deploying; the migration runs at startup. To roll back, restore the
v1.16.0 binary together with the pre-deployment database backup. Keyed publishes made after the
deployment are lost in that case.
