# Artifact MCP v1.28.0

This release hardens the preview renderer path: an attested renderer binary in every release, an
optional shared token between the server and the renderer, and an optional Chromium sandbox in
the renderer.

## Schema

Schema 40 before and after. No schema migration.

## New settings

All new settings are optional. With none of them set, the server and the renderer behave as in
v1.27.0.

Server (`artifact-mcp`):

| Setting | Meaning |
| --- | --- |
| `PREVIEW_RENDERER_TOKEN` | Shared bearer token. Every render request then carries `authorization: Bearer <token>`. 32 to 4096 printable ASCII characters without spaces. |
| `PREVIEW_RENDERER_TOKEN_FILE` | Path of a file that holds the token instead. Read once at startup; one trailing newline is removed. Setting both is a startup error. |

Renderer (`artifact-preview`):

| Setting | Meaning |
| --- | --- |
| `RENDER_TOKEN` | The same shared token. `POST /render` then requires the header and answers `401 {"error":"unauthorized"}` without it. `/health` stays open. |
| `RENDER_TOKEN_FILE` | Path of a file that holds the token instead, with the same rules as the server's file. |
| `CHROME_SANDBOX` | `1` or `true` keeps Chromium's own sandbox (no `--no-sandbox`; every other launch flag is unchanged). Default off. Any value other than `1`, `true`, `0` or `false` stops the renderer at startup. Needs unprivileged user namespaces and a user other than root. |

Neither side logs the token, and `Debug` output and error messages never contain it. An invalid
value stops the process at startup.

## Attested renderer binary

Each release now has an `artifact-preview` asset: the static musl renderer binary, built in the
release workflow from the tagged source. `SHA256SUMS` covers it, and it has its own build
provenance attestation from the same workflow as the server binary. `release-manifest.json` is
unchanged and does not name it. See [Release provenance](../release-provenance.md) for the
verification commands. A native renderer host installs this asset instead of a local build
(`preview-renderer/DEPLOY-CT222.md`, step 1).

## Configuration and compatibility

- The renderer's HTTP contract is unchanged unless a token is set. A renderer without a token
  ignores the `authorization` header, as the Node and v1.27.0 renderers did.
- Compose passes one `PREVIEW_RENDERER_TOKEN` value from `.env` to both services (the renderer
  gets it as `RENDER_TOKEN`). Recreate both containers after you change it.
- Compose keeps `CHROME_SANDBOX` off. The sandbox has not been tested in the container; the
  container restrictions stay the renderer's boundary there.
- CI's renderer job enables unprivileged user namespaces so that the sandbox tests run.
- MCP surface: no change.

## Deployment and rollback

No migration. Install the release binary as usual.

For a native renderer host such as the one in `preview-renderer/DEPLOY-CT222.md`:

1. Install the attested `artifact-preview` asset (runbook steps 1 to 6).
2. Shared token (runbook section "Shared token"): set `PREVIEW_RENDERER_TOKEN` on the server
   first, then `RENDER_TOKEN_FILE` on the renderer. In that order, no render fails during the
   change.
3. Chromium sandbox (runbook section "Chrome sandbox"): on a host that allows user namespaces
   (in a Proxmox LXC, `features: nesting=1`), set `CHROME_SANDBOX=1` and check that the renderer
   processes run under their own seccomp filter. Do not add `RestrictNamespaces=` to the unit.

Rollback:

- Renderer: remove `CHROME_SANDBOX=1` to drop the sandbox, and remove the token setting to open
  `/render` again; restart after each change. The v1.27.0 renderer binary ignores all three new
  settings.
- Server: remove the token from the renderer before you roll the server back to v1.27.0, which
  sends no token. Otherwise every render gets `401` and the gallery keeps placeholders. The
  v1.27.0 binary starts on data written by this release (schema 40).
