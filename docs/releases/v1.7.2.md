# Artifact MCP v1.7.2

The protected `v1.7.0` and `v1.7.1` tags stopped before publishing a GitHub Release or stable
image. Version 1.7.2 is the first distributable release in this feature line. The final correction
is confined to the release harness: isolated candidate boots receive their required keys, and
historical fixture containers use the runner's numeric non-root identity so cleanup is reliable.

## Schema

- Upgrading from public release v1.6.1 migrates schema 23 to schema 32.
- Migrations are forward-only and complete before the listener becomes ready.
- Frozen historical fixtures cover every boundary through schema 32, reopen idempotency,
  corruption refusal, tenant isolation, and recovery mutations.
- Schema 32 adds anchor-v2 evidence fields while retaining legacy anchors and replies.

## Release highlights

- The artifact library now has one toolbar for search, quick views, organization and category
  dropdowns, sorting, and grid or list layout. Equal-height cards replace the old left filter rail.
- The artifact viewer prioritizes the sandboxed artifact. Back returns to the library, while
  feedback, details, sharing, history, audience, reactions, theme, download, and deletion live in
  compact menus and the inspector.
- Anchor v2 persists DOM and selection evidence through Rust, Node, HTTP, and MCP. The browser adds
  positioned comments, threaded replies, stale-revision handling, and deterministic Copy prompt
  output.
- Verified publisher ownership governs member Hide, Show, and Delete controls. Administrators can
  edit publisher-key labels, roles, and verified owners without rotating credentials.
- Organization-scoped Discord notification threads and guarded two-way replies remain opt-in.

## Deployment notes

1. Create and test a backup of the database, artifact bodies, previews, and deployment
   configuration before starting this release.
2. Record the current binary or immutable image digest as the rollback target.
3. Verify `WEBHOOK_ENC_KEY` and `AUDIT_LEDGER_HMAC_KEY` are configured without printing either
   value. Each must be canonical base64 for exactly 32 bytes.
4. Keep `DISCORD_INBOUND_ENABLED` absent or set to `0` for the initial rollout.
5. Deploy the checksummed, attested binary or immutable OCI digest from `release-manifest.json`.
6. Wait for `/health` to return `{"status":"ok"}` and confirm schema 32 before enabling traffic.
7. Keep Artifact MCP feedback and publishing available while Discord is disabled, then canary
   inbound synchronization separately if it is needed.

## Configuration changes

- The UI and anchor-v2 additions require no new environment variable.
- `AUDIT_LEDGER_HMAC_KEY` is mandatory at startup.
- Discord credentials remain per organization, write-only in the browser, encrypted at rest, and
  absent from API responses and release evidence.
- `DISCORD_BOT_TOKEN` remains a migration fallback, not the ongoing organization credential.

## Compatibility and rollback

- Legacy MCP behavior from v1.6.1 remains available alongside the newer contract.
- Node and Rust parity checks cover anchor-v2 persistence and projections. Legacy feedback remains
  readable, with new fields projected as explicit nulls where absent.
- A binary-only or image-only rollback is unsafe after schema 32 opens. Stop the service, restore
  data and deployment configuration from the pre-migration backup, then start the previously
  recorded binary or immutable image digest.
- Leave inbound Discord synchronization disabled throughout rollback.

None.
